## 冻结内容与口径

- `stage_jobs.jsonl`：按当前默认 phase 规则形成的 26 个封口任务。它们是固定生成输入，不是人工 stage 金标。
- 四份事件 JSONL：包括 finish 后状态通知，不包含后验 `verification.log` 或作者参考解。
- `token_preflight.json`：26 个生成块均通过真实 Qwen tokenizer 预检，最大输入 2434 token；总预算 8192，输出预留 512，无输入缺口。
- `protocol.json`：参考与输入哈希。构建脚本禁止静默覆盖已变化的冻结文件；修正需要新版本，不能看过输出后改答案。

40 条事实位于封口阶段，其中关键结果 28 条；6 条事实仍在开放末段，其中关键结果 5 条。两份异常退出会话没有补造 finish。评估应分别报告封口任务的覆盖、全部关键结果的覆盖和开放部分，不能把未触发生成算成成功，也不能隐藏该部分。

注释是有范围的 AI 参考，不是人工金标或完整阶段真值。上下文事实不要求摘要逐项列出；重复失败可以合并，但要保留正确对象、时间、范围和引用。此处没有边界 F1 或 failure alarm 标签。

### 工程可运行不等于语义达标

对全部输出做单轮非盲 AI 复核（参考先于输出冻结），并将 claim 支持与事实覆盖分开：

| 指标 | 本轮结果 |
| --- | --- |
| claim 引用支持 | 25 获支持、8 部分支持、6 不支持，共 39 |
| 已封口的全部事实 | 17 完整、19 部分、4 遗漏，共 40 |
| 已封口的关键事实 | 10 完整、16 部分、2 遗漏，共 28 |
| 开放末段 | 6 条事实，其中 5 条关键事实；没有生成任务 |
| 已封口的失败／零测试／异常 | 20/20 保留粗粒度负向结果；不保证原因、条件或诊断细节正确 |

这些是固定四份合成会话的 AI 判断，不是人工准确率。完整覆盖按语义实质而非逐字匹配；部分覆盖表示只保留粗粒度事件、遗漏条件／诊断或出现错误细节。一个 claim 可能正确覆盖某条事实，但另一个子句仍有错误，因此“事实覆盖”和“整条 claim 支持”不会一一对应。引用重叠仅用于核对归属，不自动决定覆盖。

若只看完整覆盖，封口关键事实为 10/28；若看实际运行全量关键事实，则 10/33，另有 5 条开放末段关键事实不可忽略。不能把后者全部归责于抽取模型，也不能为提高成绩将其从端到端覆盖报告中隐藏。

### 实际瓶颈

1. **引用选择错误。**6 条不支持的 claim 多只引用 unittest 命令或编辑动作，却写失败数、返回值、异常或编辑回执。相关结果有时确实出现在同阶段其他观察里；这是引用／来源归因错误，不全是凭空捏造结果。agent_assertion 标签也不能把命令变成结果声明。
2. **因果、方向和变化范围失真。**把 old_str 不匹配改写为“只在原版本出现”；把实际少一个末尾元素说成“多了第五个元素”；把已经存在的初始零说成这次新增。
3. **代码条件和事件身份不精确。**把 truthy 过滤写成 non-null；把 agent finish 自述称为 commit message。
4. **摘要过泛。**多个修改阶段只保留“文件已编辑”，省略 seen/input-order、循环边界或 base.copy 等具体变更。粗粒度负向结果保住了，但详细事实覆盖仍弱。
5. **关键自述遗漏。**bounded_chunks 的“已修复但未自动验证”声明，以及 config_overrides 的“已提交”声明没有被准确保留。这不代表抽取器直接声称这些任务成功，而是账本丢失了需要审视的 agent 断言。

本轮暂不能将问题简单归为模型参数太小或 stage 不准确：输入、封口和模型均已固定，仍观察到明确的引用与表述问题。它也没有测出划分改善会带来多少收益。v4 的 42 条输出与本轮 39 条属于不同任务、参考范围不同，不直接比较“准确率涨跌”。
