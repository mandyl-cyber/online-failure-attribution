# 在线 stage 的 claim 摘要器：设计、挑战与实施计划

日期：2026-11-17。状态：v3 的离线开发协议与输入/校验已实现；服务端约束解码、线上 backend 和边界确认策略尚未实现，语义质量待远程验证。

修订：结合本地 OnlineTAS 全文（含附录）补充边界确认、长短期信息分工和延迟评估。以下候选边界缓冲、确认策略及相关实验均是待验证设计，不代表现有运行器已支持；不改变先稳定摘要器的实施优先级。

## 1. 设计结论与范围

保留当前主线：轻量在线分段 → stage 封口 → 生成多条 claim 形式的阶段摘要 → 为后续在线风险报警提供历史上下文。

本轮目标是先提高摘要器的稳定性，不先开展分段质量分离实验，不新增分类器、语义关系图、常驻审核模型或自动干预策略。
分段质量可能影响摘要，但现有短阶段中的重复和误读已经说明抽取器自身需要改进；暂不把边界 F1 当作抽取工作的前置门槛。

一个 stage 是一次组织和入账单位，可以生成零条、一条或多条 claim。多条 claim 的集合就是该 stage 的摘要，不再另生成一份独立自由文本摘要。
账本当前采用阶段容器与 claim 记录；只保存确定的来源关联。它尚不是经过验证的因果树。
后续在线模块定位为 failure alarm：结合历史摘要与当前 stage steps 判断是否存在需要复查的风险，允许证据不足；不预设任务已失败。

## 2. Claim 的含义与职责边界

Claim 是有来源、可回查的语义记录，不是系统认证的世界事实。

以下三条都可以正确地记录一个阶段：

- 工具报告目标测试失败。
- agent 判断失败可能由依赖版本引起，尚未验证。
- agent 计划升级依赖后重跑目标测试。

第二条中的判断即使错误，忠实记录它也有价值；后续报警可能正需要定位这个错误前提。
“摘要忠实”与“agent 判断正确”是两种评价，不得混用。

摘要器负责保留关键观察、判断、计划、变化与结果，明确其来源、条件和时间范围。
摘要器不负责主动诊断危险步骤、不判断最终任务成功、不生成因果解释、不自动纠正 agent、不决定回滚或人工介入。

每条 claim 表达一个可以独立核查的要点。必要条件属于这个要点，不能为了原子性删掉：

- 合适：显示的代码在 axis != 0 时抛出异常，默认 axis=0。
- 不合适：不支持 axis。
- 合适：提交说明称此次修改用于内联装饰器，工具确认提交完成。
- 不合适：装饰器行为已正确修复。

## 3. 当前实现与实验证据

### 3.1 已有能力

- `segmenter` 已有在线分段和阶段后台作业的基础设施；规则/dry-run backend 与远程语义 pilot 是不同路径。
- v2 由程序编号证据片段，模型返回 ID，程序还原原文范围，解决了要求模型计算字符偏移的问题。
- 远程本地 Qwen 已完成真实抽取调用；原始响应、失败和配置均有保存。
- 已有运行恢复、输入指纹、格式和引用归属校验；这些检查不证明语义支持。

### 3.2 最新结果

| v2 开发样本 | 6/6 | 29 | 21 |

## 4. 当前挑战与对应改动

| 挑战 | 已观察到的问题 | 本设计处理方式 | 不能保证的部分 |
|---|---|---|---|
| 协议不稳定 | 多余顶层数组、缺逗号、objects/引用数组超限 | 简化模型输出；验证真实约束解码能力；仍做客户端校验 | JSON 合法不等于语义正确 |
| 引用错位 | 引用同文件中不相关代码，遗漏比较另一侧 | 以动作—观察组织输入；为长块保留来源上下文 | ID 合法不能证明蕴含 |
| 状态误读 | 未跟踪被说成未修改；Git身份被说成当前用户 | 短任务契约、针对性负例、保持原始表述范围 | 不靠泛化规则覆盖所有工具语义 |
| 意图升级为事实 | commit message 被当成实现完成 | 保留 agent_assertion 与 tool_observation 区别，正文说明来源 | 工具输出也可能只是转述计划 |
| 选择与冗余 | 文件大小占配额；一次编辑重复六次 | 取消六条统一硬目标；重点保留变化、约束、结果、关键判断 | 单靠放宽数量不会解决选择问题 |
| 信息压缩损失 | 条件、失败尝试、未解决事项遗漏 | 保留条件；原文存档；评价关键内容覆盖 | 不宣称无损摘要 |
| 异步不可用 | 阶段已封口但摘要未生成 | 明确 pending/failed，保留原始 steps，记录实际可用时刻 | 摘要耗时不能等同在线每步延迟 |

## 5. 最小架构

```text
持续到达的动作和观察
    → 原始记录持久化、动作—观察配对
    → 轻量划分器输出当前边界分数
    → 确认策略维护候选边界，仅调整未封口尾部
    → 确认 stage 并封口
    → 冻结阶段输入快照，后台排队
    → 程序组织输入
    → 一次模型调用生成 claim 数组
    → 程序做结构与来源校验
    → 原子写入阶段摘要及 claim

原始证据始终保留，供后续风险报警回查。
```

这是一个摘要器内部的流程，不是多个神经模块。第一版不增加在线 LLM 审核调用。
正常规模的阶段每次封口调用一次；长阶段超预算不静默切成许多额外调用，先显式标记 blocked_input_budget，另行评估输入组织。

### 5.1 预测与提交分离

轻量模型回答“这里是否可能开启新阶段”；确认策略回答“是否已有足够证据提交该边界”。分数不直接等同正式阶段，也不因一次目的标签变化就必然切分。

第一轮保留即时提交 D=0 基线，另比较固定等待 D=1、D=2 个完整动作—观察步骤的策略。固定等待本身不会提高准确率：候选必须利用新增的前缀信息重新评分，才能检验其价值。具体评分特征、阈值及冲突处理在开发任务上确定后冻结，不预先声称 D=2 最优。

约定边界 b 表示新阶段从步骤 b 开始，旧阶段终点为 b-1。若在 b+D 时确认：

- 边界判断最多使用截至 b+D 的可见信息；这属于有界延迟输出，不是步骤 b 当时即可获得的即时预测。
- 旧阶段摘要的本阶段证据仍只到 b-1；b 至 b+D 的步骤属于未封口的新阶段，不能混入旧阶段摘要。
- 候选可被确认或撤销；初版不实现任意历史边界移动。缓冲区中多个候选按时间顺序处理，明确取消和合并理由，确保已提交区间无重叠、无遗漏。
- 每个候选必须在固定等待到期后作出决定，不因置信度不足而无限延期。流暂时停止时不虚构未来步骤；显式结束时按已见前缀处理尾段，并标记 end_of_stream，单独统计。

这是拟议生命周期，不是已经确定的最优算法。D=0、1、2 的所有比较必须保存边界位置与真实决定时刻，避免把延迟预测按即时结果计分。

### 5.2 稳定化与短阶段保护

OnlineTAS 表明，抑制预测抖动可能改善段级质量，但也会推迟真实转折。我们可以在固定延迟试验后单独比较置信度阈值或滞回策略，不同时叠加所有机制。

不直接套用视频帧的最小段长度，更不把训练集中最长轨迹的固定比例用作编码阶段长度。编码步骤长度不均，一步编辑、失败验证或明确转向都可能重要；最短长度只能是可消融的软偏好，不能强制吞并短阶段。

置信度高不代表判断正确。阈值只能处理部分抖动，不能解决高置信误切、同目的下的子目标切换和任务中断。是否采用确认策略，以独立任务上的收益、短阶段召回及延迟代价共同决定。

### 5.3 长短期信息的职责

| 信息层 | 保留内容 | 当前用途与限制 |
|---|---|---|
| 近期步骤与未封口阶段 | 动作、观察、错误、验证、原始证据引用 | 供轻量分段及未来报警读取；具体输入窗口与模型配置一起冻结 |
| 已封口阶段的 claims | 有来源与时间范围的关键观察、判断、计划、未解决事项 | 提供较远历史摘要；暂不反向影响分段器 |
| 持久化原始轨迹 | 完整事件与版本信息 | 根据引用回查；摘要不能替代原始证据 |

这里区分的是使用方式，不要求新增三个神经模型。模型输入可以有预算，持久化记录不能因预算而被覆盖。读取历史时，未解决问题、失败验证和关键条件不应仅因年代较早就被丢弃；具体检索/保留算法留待报警阶段验证，不在摘要器内新建复杂记忆调度器。

OnlineTAS 将片段压成学习到的向量，我们生成可读 claim，两者不是同一种记忆。第一版不递归压缩 claims、不自动构建语义依赖边、不让摘要错误通过反馈链影响后续分段。

## 6. 输入设计：配对事件，完整来源

### 6.1 输入单元

以一个动作及其对应观察作为输入组织单元，保留原始 step ID。不能仅靠相邻位置强行配对；并行工具事件使用原生关联 ID，无法配对时明确缺失。

每个单元包含：

- step_id、动作原文、观察原文；
- action_ref、observation_refs；
- 程序实际掌握的工具名称、对象路径等元数据；未知不猜；
- 可获得时记录事件版本/文件内容哈希，区分两者；
- 原始可用顺序以及输入裁剪/缺失标记。

长观察仍可分块，但不能让正文只剩无上下文的 e0031。展示标签建议采用 S27.observation.1；全局身份由 run_id、原始事件及块位置确定，不靠展示名称保证唯一。
每块与原始文本保持精确映射；块应携带父记录与可信路径/命令上下文，不能让模型自行补全文件归属。
块大小、切块策略属于版本化输入配置。初始沿用现有上限以减少变量，后续只在有证据时调整。

### 6.2 任务与历史上下文

可提供截止时刻实际可见的简短任务说明，缺失则 null，不从最终答案或标签反推。
第一版不递归输入整份历史摘要，避免摘要误差反复传播。阶段引用的早期上下文若不可见，模型应缩小陈述或表示无法确认。
必要前序原文背景是后续可消融选项，必须与本阶段证据明确区分，不能把旧事实重复记成新事件。

### 6.3 只允许前缀信息

每次作业固定：stage_start/end、sealed_at_seq、input_cutoff_seq、source_hash。
摘要证据仅来自该阶段及明确允许的前序背景，不因延迟封口就把后续阶段的步骤纳入本阶段陈述。
sealed_at_seq 可以晚于 stage_end；它不等于模型实际完成时间。
gold 阶段仅用于离线实验，不能进入真实在线划分路径。

## 7. 输出契约：模型负责语义，程序负责身份

协议名：`stage-claim-summary-v3`。独立开发运行器 `remote_pilots/openhands_smoke/claims_v3.py` 已支持；当前在线账本 backend 尚未接入。

模型只生成 text、source、evidence_ids。一条 claim 不混淆来源，例如将工具报告的失败与 agent 的解释分开：

```json
{
  "claims": [
    {
      "text": "工具报告目标测试在该次运行中失败。",
      "source": "tool_observation",
      "evidence_ids": ["S12.action", "S12.observation.1"]
    },
    {
      "text": "agent 将依赖版本列为失败原因的待验证假设。",
      "source": "agent_assertion",
      "evidence_ids": ["S13.action"]
    }
  ]
}
```

这里的证据 ID 仅为协议示例，真实生成只能选本作业给出的 ID。

`source` 表示正文记录的认识来源，不是输入字段类型：工具显示 agent 的待办时仍可记录 agent_assertion。
显示源码时允许 tool_observation，但正文应写“所见声明/分支”，不能写成实际执行成功。
新推理结论不属于第一版摘要器职责；允许忠实记录 agent 已有推理，但不得自己发明解释。

程序补齐：claim_id、run_id、stage_id、source_step_ids、原始 evidence_refs、输入版本、模型/提示指纹、created_at、available_at_seq。
暂不要求模型输出 objects、kind、confidence、depends_on、supports、根因、字符偏移或复制引文。
可靠对象元数据可由程序附带；无法可靠获取则为空，不用同路径猜依赖。

## 8. 摘要内容与数量

指导模型回答四个问题，但不强制四个字段或类别配额：

1. 观察或确认到了什么关键内容？
2. 做了什么变化，有什么观察结果？
3. agent 提出了什么重要判断或下一步计划？
4. 哪些问题仍未解决，或者证据没有给出结论？

探索、计划、失败尝试都可以入账。不能只保留编辑与测试，否则难以捕获后续风险所依赖的错误前提。
阶段封口仅表示输入区间固定，不代表子目标完成。中断、转向、尚未验证的假设都应忠实保留；不能为了生成完整故事把“尝试修复”写成“修复完成”。
已知失败必须按失败记录，不能压缩成“完成测试”；没有验证证据也不能自动断言“整个任务从未验证”。

取消所有阶段统一 maxItems=6 的语义配额，保留可配置的整体 token/字节资源限制；具体预算在开发集依据输入长度和输出覆盖率确定后冻结。
该变化必须单独版本化，不将 v2/v2.1 旧失败重新解释为通过。
输出因长度截断则不提交半条摘要；不能靠删除尾部 claim 伪装完整成功。
finish_reason=stop 也不证明语义完整，完整性只能通过覆盖评价估计。
不做自动语义去重；相同文本在不同版本/步骤可能代表新的事件。只对同作业重放做幂等处理。

## 9. 协议稳定性与降级

优先检查远程服务是否实际执行约束解码。把 JSON Schema 放进 prompt 或传入不被服务识别的 response_format，都不是强约束。
若适配 XGrammar 等能力，应通过故意诱发顶层数组、额外字段、非法 ID 的探针验证；支持哪些 schema 约束必须逐项实测。
约束解码只能约束格式和可表达的 ID 范围，不能证明事实或引用蕴含。服务端改变作为独立实验配置记录。

客户端检查 JSON、必需字段、枚举、证据归属、原文哈希、前缀范围、资源限制；一项失败则该作业不入正式摘要。
不模糊匹配引用，不自动补逗号，不把删字段后的响应算作模型原输出成功。
保留 request/raw_response/error/usage；第一版仍一次尝试。未来任何重试都要独立记录次数和成本。

失败时保留原始 stage，状态 failed。成功的零条输出单独标记 ready_empty，不能与失败或“无风险”混淆。
无需额外 LLM 生成兜底摘要；后续报警可回看对应原始步骤或明确暂缺历史摘要。

## 10. 在线生命周期

拟议状态：pending → running → ready / ready_empty / failed / blocked_input_budget。
输入不完整另带 completeness 标志，不能用 ready 掩盖源证据缺失。

- 封口后冻结作业快照；主事件接收不等待抽取完成。
- 输出校验通过后整批原子提交，确保一 stage 多条 claim 不出现半批可见。
- 幂等键包含 run、stage、输入哈希和协议/模型配置。相同内容不同实际执行事件不能简单去重。
- 在时刻 t 进行报警，只能使用 available_at_seq ≤ t 的摘要。后台完成的摘要不能回填成过去已可用。
- pending/failed 阶段保留原文入口。当前 stage 的 steps 与摘要队列状态都对下游可见。
- 重启恢复时不自动重发已尝试作业；未完成 reserved/running 状态需明确标注，不能误算成功。

需要测 queue_wait、服务耗时、从封口到摘要可用的总延迟、队列积压和抽取 token。
单次请求中位4–7秒不能直接推出延迟封口应为几步；队列吞吐与 agent 步速是不同约束。
本阶段不实现历史 stage 回改后自动重算全部账本；若后续支持，须有独立 revision 与失效机制。

### 10.1 三种延迟分别记录

1. 边界确认延迟：候选边界所在步骤到提交决定的步数与墙钟时间。
2. 摘要可用延迟：阶段封口到摘要原子入账，包括排队与生成。
3. 报警响应延迟：触发条件成立到报警输出；这是未来报警模块的指标，当前没有效果结论。

固定两步不等于固定两秒；长工具调用可能让两步等待很久。选择边界窗口时优先看边界收益和可接受的响应延迟，不以平均 claim 生成耗时直接换算。摘要耗时用于配置并发、输入预算和积压策略。

主事件循环在摘要 pending 时继续推进。阶段刚封口但摘要未完成时，下游只能读取已可用 claims 与允许的原始步骤，必须显式看到历史摘要缺口，不能把缺口理解为没有风险。记录封口、完成的墙钟时间与单调可用顺序；若沿用 step 序号，需额外区分同一步内的完成先后，防止回放泄漏。

积压超过预先配置的预算时发出工程状态提示并保留未处理作业，不静默丢阶段，也不把摘要队列反压到 agent 的执行循环。具体并发上限与阈值在远程服务实测后配置。

## 11. 验收方法

先冻结输入与任务组，再评估摘要器；当前不要求先跑分段分离实验。
开发样本可以包含现有问题案例；验收任务必须与新一轮提示/训练选型任务隔离，另标记是否在项目历史中用过。
同一轨迹重叠阶段、相同证据不得按独立样本计算置信区间。

样本应覆盖：计划、探索、编辑、验证、混合阶段，并包含成功/失败、只有命令无结果、源码与真实运行、Git身份/状态、跨片段条件等负例。
类别仅用于采样覆盖，不要求在线训练类别模型。

| 指标 | 定义与注意事项 |
|---|---|
| 作业成功率 | 合法完整入账请求 / 全部尝试；失败不删除 |
| 证据忠实度 | 已生成 claim 中所有关键子断言均被所引证据支持的比例；按来源正确转述错误假设可算忠实 |
| 引用支持 | 区分 ID 存在、引用相关、完整支持；不能合并 |
| 关键内容覆盖 | 对阶段参考要点检查保留情况；空输出不能获得虚假的完美效果 |
| 严重语义错误 | 条件反转、失败说成成功、计划说成执行、观察者/对象/版本错置，逐例记录 |
| 冗余 | 同一范围内重复同一要点；跨时间重复不直接算重复事实 |
| 成本与延迟 | 输入输出 token、整体压缩率、调用数、生成与排队时间 |

先为少量阶段建立带证据的参考要点，而不是只审核模型已经选择输出的句子；记录不可判断项和必要上下文。
可以采用 AI 复核启动工作，但需标记 reviewer_type=AI，不能宣传为人工准确率。未来人工抽检可校验审计偏差。

工程测试要求：固定合法输入的结构与映射测试全部通过；约束解码探针不得默默失效；失败/重启/输入超限可追踪。
语义进入扩大验收的条件：开发严重错误有明确修复，冻结验收样本没有出现同类关键反转，且覆盖和成本没有明显退化。
这是小规模推进门槛，不是安全保证或总体误差率上界；数值质量门槛需在验收运行前结合样本规模冻结，不能看完结果再选。

### 11.1 边界确认的独立验收（摘要稳定后的后续工作）

这项实验检验在线提交策略，不是要求当前先做分段质量与摘要质量的全量分离实验。固定同一个边界模型、输入定义、任务分组及阈值选择流程，先比较 D=0、D=1、D=2；不同时更换目的标签、文本编码器和摘要模型。

必须同时报告：

- 边界位置精确匹配及 ±1 步 F1、精确率、召回率、预测切点总数。
- 提交时机：实际确认延迟的步数/秒数分布，未决候选数量；即时与延迟输出分开报告。
- 结构副作用：碎段数量、短阶段漏检、阶段长度分布，以及被中断/转向案例。
- 运行成本：每步计算耗时、状态内存、暂停/结束/恢复后的区间一致性。

若增加段重叠指标，明确是无类别区间匹配还是类别敏感匹配，不能将其与 OnlineTAS 的 F1@{10,25,50} 或当前边界 F1 混称“准确率”。已有 D1 容差评估结果也不等于一个实际等待一步的算法已获得提升。

阈值在开发任务选择，验收按任务隔离；区间估计按任务配对重采样，不能把同轨迹步骤当独立样本。没有可靠收益则继续 D=0，不因引入缓冲就默认替换线上策略。

## 12. 实施顺序与决策点

| 阶段 | 工作与交付 | 决策 |
|---|---|---|
| P0 固定契约 | v3 schema、内容标准、正反例、样本清单、证据来源与时间说明 | 仅文档与数据，不调用模型 |
| P1 最小输入适配 | 动作—观察组织、稳定证据映射、移除必填 objects；保持原文与异常可见 | 本地恢复/映射/拒绝未来信息测试通过 |
| P2 协议能力 | 检查自建 Qwen 服务；约束解码与仅提示版本单独记录 | 不将结构改进误报为语义改进 |
| P3 小批语义验收 | 同一冻结输入上运行、逐条核验与参考要点覆盖 | 未通过则定位任务/输入/模型问题，不扩大48条 |
| P4 模型决策 | 若短配对输入仍不稳定，用小批更强模型作能力诊断；或用已复核目标做SFT/LoRA | 先证明目标质量，不能用原模型错误输出自训 |
| P5 旁路接线 | 新摘要 backend 接入后台队列，验证真实可用时间与失败降级 | 才开始账本对在线报警的价值对照 |

主要表示变化可组合成一个明确命名的 v3 工程基线，但不能由总分变化推断单项贡献；服务端解码、模型更换和训练分别版本化。
保留同模型简短自由文本摘要或原文窗口作为后续低成本对照，以检验 claim 结构是否真的有用，不现在扩成新的产品模块。
当前不采用 RL：没有可用的在线报警/干预回报来训练摘要策略。先做监督目标和忠实性评价。

P3 摘要稳定后，可另开分段支线：先冻结提交协议并验证 D=0/1/2，再决定是否需要因果 TCN/GRU。保留当前结构逻辑回归作对照；候选神经模型直接用现有边界监督训练，目的类别只作为可消融辅助任务，不要求先补全七类标注。

OnlineTAS 的交叉熵加相邻类别概率平滑，不能原样施加到稀疏的边界标签上：相邻边界概率强行相同可能抹去真正边界。若研究时序损失，需为边界任务单独定义、消融，并检查短阶段漏检。该支线不阻塞 P0–P3，也不预设神经模型优于现有轻量基线。

现有远程硬件可用于同规模 Qwen 试验；本设计不要求立即采购或升级。约束解码适配、模型更换和训练的具体环境需求需实施前实测。

### 14.1 OnlineTAS 阅读结论与证据边界

依据本地 16 页全文（正文及附录）：

- 第 4 页：长短期记忆共用固定预算，历史片段经卷积压缩为向量。支持分层保留信息的方向，不证明语言摘要的忠实性。
- 第 5 页：严格 online 每次只保留当前窗口末帧预测；semi-online 收满片段再输出所有位置。后者不能当即时输出。本文的候选缓冲是迁移设计，论文没有验证我们提出的 D=1/2 编码步骤策略。
- 第 5–6 页：后处理在低置信且长度条件满足时沿用前一输出标签，没有改写已输出历史。算法 2 的计数器在另一分支直接清零，和正文“段长度”的含义需要结合实现核对，不能照抄成我们的阶段年龄。
- 第 6、9 页：Breakfast 的 online 模型经后处理，逐帧 Acc 从 56.7 降到 52.9，段级 F1@50 从 9.3 升到 30.5。该指标不是我们的 ±1 步边界 F1。
- 第 7、9–10 页：过大窗口可能稀释短动作；边界有延迟；高置信错误、中断动作和无限长历史仍是限制。稳定化不能解决全部语义错误。
- 第 8 页表 8 的部分 online 行与第 6 页表 1 对应行不一致；引用定量比较时须指定表和设置，当前不据此宣称可复现的迁移增益。
- 第 14–16 页：附录解释因果卷积和另一骨干适配。因果性必须检查整个输入/注意力/记忆路径，不能只因用了 causal convolution 就认定无未来信息。
